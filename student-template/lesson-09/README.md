# 第09课 · 筛查阳性之后怎样安排复核

## 先想一个问题

有一种检测，能查出90%的故障。现在，一台设备的检测结果是阳性。你能据此说，它有90%的可能真的故障吗？

先别急着回答。“故障设备有多大可能被查出来”和“查出来的设备有多大可能真的故障”，问的不是同一件事。本课先用具体台数讲清这个区别，再用它解决一个实际安排问题。

设备保障部门明天要检查1500台设备，但只能进一步复核其中90台。你需要帮部门决定：两组设备各用哪种初筛方法，有限的复核名额怎样分配。

## 这节课怎样学

建议先读[概念与例子](LEARN.md)。从1000台设备的检测结果开始，看看阳性中为什么会有不少设备其实没有故障；再读20台设备的小例，学会计算复核之后还剩多少故障没有发现。

接着，使用本页的数据完成自己的比较。可以用Python、电子表格，也可以请AI帮助计算和写代码。遇到文件、命令或提交问题，再查[操作帮助](SUPPORT.md)。

本课的数据都是为教学编制的，不代表某家单位的真实设备。

## 你拿到的数据

两组设备的情况如下。这里的故障比例是检查前的估计，叫作**基础率**。

|设备组|明天检查的台数|预计故障比例|每台未发现故障造成的损失|
|---|---:|---:|---:|
|常规组（routine）|1000|2%|60|
|重点组（priority）|500|10%|100|

每组可以选择下面一种初筛。选好后，该组全部设备都要做这项检查。

|初筛方法|故障设备检出阳性的比例（敏感度）|正常设备判为阴性的比例（特异度）|每台费用|
|---|---:|---:|---:|
|sensitive|90%|95%|1|
|precise|80%|99%|2|

sensitive能查出更多故障，但也会把更多正常设备报成阳性。precise误报较少，却会漏掉更多故障，而且费用较高。因此，方法的名字不能直接告诉你该选哪一个。

两张表分别来自 `data/inference-09-14/alert_groups.csv` 和 `screening.csv`。本课必做只用第一份文件的 `base` 列，也就是上表的2%和10%；`base_low`、`base_high` 暂时不用。更多字段说明见[数据说明](../data/inference-09-14/README.md)的第09课部分。

还要遵守四个条件：

1. 初筛总费用不能超过2000。
2. 复核最多安排90台，只能从初筛阳性的设备中选择。
3. 每次复核另付3，不占用上面的初筛预算。计算总费用时要把它另列出来。
4. 本题假设复核不会判断错，而且查出的故障都能修复。同一组的阳性设备之间没有更多风险信息，因此在组内随机选择复核对象。

费用和损失使用相同的计量单位。

## 你的任务：比较两套安排

先拟定一套你认为合适的安排，再找另一套可行安排作比较。每套安排都要写清：

- 常规组和重点组分别用哪种初筛；
- 90个名额准备怎样分给两组，是否给某组保留最低名额。

例如，你可以优先把名额给“每复核一台，预计能减少更多损失”的组；也可以为另一组保留一部分机会。具体选多少、为什么这样选，由你根据计算决定。

先检查两套安排是否都满足预算和名额限制，再用同一批设备、同样的检验性能和损失标准比较。至少作出并解释两项选择：初筛怎么选，复核怎么分。它们可以同时体现在这两套安排中，不用为每项选择另外做一套实验。若两项都变了，比较的是整套安排的效果，不能把所有差异只归因于其中一项。

报告中用一张表列出每套安排的：

- 两组各复核多少台；
- 两组预计各有多少故障仍未发现；
- 未发现故障造成的损失；
- 初筛费用、复核费用。

如果还想比较“费用加损失”的总数，可以再加一列，并说明加了哪些项目。

## 从哪里算起

先挑一组设备和一种初筛，把下面四步算完整：

1. 这组预计有多少台故障，多少台正常？
2. 故障设备中有多少会报阳性？正常设备中有多少会误报阳性？
3. 在所有阳性设备中，真正故障的比例是多少？
4. 用这个比例计算：复核若干台后，预计能查出多少故障，还剩多少没有发现？

[LEARN](LEARN.md)会带你完整算一遍。正式报告也要保留一个这样的计算例子，让读者能看懂你的数是从哪里来的。

本课用预计台数安排名额。名额必须是整数；你可以把预计阳性台数向下取整作为规划表中的上限，并注明这一做法。真正执行时，要以当天实际阳性台数为准，有剩余名额再按你的规则调整。预计阳性58.5台，不表示每天都只能出现58台阳性。

本课不要求找出所有安排中的最优方案，也不要求模拟每天人数的波动。能够比较两套可行安排，并解释“得到了什么、付出了什么”，就完成了主要分析。

## 最后交什么

写一页左右的建议，配上比较表和可以重新运行的计算程序。可以直接使用[报告提纲](report.md)。

建议中说明：你推荐哪套安排，为什么；它有什么代价或不足；哪项现实条件变化后，你可能改变建议。最后这一点用文字说明即可，不必再计算三个情境。

第一次运行示例时，在学生仓库根目录输入：

```bash
python3 scripts/course.py start 09
python3 scripts/course.py run 09
```

它只会生成教学小例，不会替你完成1500台设备的正式比较。怎样找结果、换成自己的程序和提交，见[操作帮助](SUPPORT.md)。

AI可以帮助构思、编程、计算和写作，不需要提交AI对话记录，也没有额外答辩。提交前请核对一个具体计算，并确认报告中的数字能在结果文件里找到。

## 还有时间，可以再想一步

假如实际故障率比预计的高，原来的安排还合适吗？完成必做后，可以用 `base_low` 或 `base_high` 再算一次：保留同一套分配规则，按新的风险重新分配名额，看看建议是否改变。

这是选做，不影响必做任务的完成。没有额外检验数据时，也不要直接假设两种初筛相互独立，再把它们连续使用。
