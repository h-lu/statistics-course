# 第09课支持路线 · 从筛查结果到复核安排

## 先知道今天要交出什么

你要为设备保障部门交出一套明天能执行的复核方案。最终至少包括：

- `report.md`：说明各来源组使用哪种初筛、阳性后按什么顺序复核，以及名额不足时怎样处理；
- `artifacts/`中的结果表：列出各组预计阳性数、预计故障数、阳性预测值、安排复核数、预计漏检数、费用和复核分钟数；
- 可重复运行的分析程序：比较主方案、一个合理备选方案，以及低、基准、高三种基础率情境。

入门跟做只帮你建立第一张可核对的流量表，不能代替以上标准任务，也不会预先给出应选方案。

## 核心概念与原理

### 先分清两个方向相反的条件概率

**敏感度**是在真实故障设备中被初筛检出的比例，分母是真实故障设备。**阳性预测值（positive predictive value，PPV）**是在初筛阳性设备中预计真正故障的比例，分母是全部初筛阳性设备。前者高，不保证后者也高，因为现场故障的**基础率**还会改变阳性中真故障与假警报的构成。

小例子：100台设备中预计10台故障。某初筛检出其中8台，同时让18台正常设备呈阳性。敏感度是`8/10=80%`，阳性预测值是`8/(8+18)≈30.8%`。两个比例的分母不同。

### 从概率转成设备流量

对一个来源组，预计真阳性数可写成“每日台数×基础率×敏感度”；预计假阳性数可写成“每日台数×(1−基础率)×(1−特异度)”。两者相加才是预计需要复核的阳性设备数。期望台数出现小数，表示长期平均流量，不表示现实中有半台设备。

### 容量与期望损失共同约束方案

一天1440分钟、每台复核12分钟，意味着最多安排120台复核。初筛预算与复核容量是两种不同约束。**期望损失**把不同后果的发生概率乘相应损失再相加；它是比较规则的规划量，不是已经发生的实际损失。

## 基础练习（可信起点）：入门跟做

先在**仓库根目录**打开终端，完整运行：

```bash
python scripts/course.py start 09
python scripts/course.py run 09
```

第二条命令成功时，终端会提示概览已经写入`lesson-09/artifacts/starting_inventory.json`。打开这个文件；它只是数据起点，不是本课答案。若文件没有生成，先按后面的排错顺序处理，再继续。

### 第一步：确认数据和字段

- **动作**：运行`python scripts/course.py run 09`，打开`lesson-09/artifacts/starting_inventory.json`，再读`data/inference/README.md`中两张筛查表的说明。
- **目的**：区分历史验证性能和现场基础率，避免把验证样本中的故障比例当作现场比例。
- **成功信号**：概览中出现`screening_groups.csv`与`screening_validation.csv`；你能指出`daily_volume`、`base_rate`、`true_positive_n`、`true_negative_n`和`test_cost`的含义。
- **反思**：哪张表描述“初筛有多准”，哪张表描述“明天有多少设备和多少故障”？

### 第二步：手算一行验证性能

- **动作**：任选一行验证汇总，在纸上写出敏感度=`true_positive_n/condition_positive_n`，特异度=`true_negative_n/condition_negative_n`。再让程序计算同一行并核对。
- **目的**：先确认每个分母，再把性能用于现场流量估计。
- **成功信号**：手算与程序结果一致，数值位于0到1之间，并保留`group`和`test`作为行标识。
- **反思**：这里为什么不能用`true_positive_n/(true_positive_n+假阳性数)`当作敏感度？

### 第三步：建立一组一方法的流量核对

- **动作**：任选一个来源组和一种初筛，按基准基础率计算预计真阳性、假阳性、全部阳性及PPV。把计算写入自己的结果表。
- **目的**：把条件概率转换成明天需要处理的设备数量。
- **成功信号**：全部阳性等于真阳性加假阳性，PPV等于真阳性除以全部阳性；表中同时保留台数与比例。
- **反思**：若基础率下降而敏感度、特异度不变，PPV通常会向哪个方向变化？为什么？

### 第四步：先做可实施性检查

- **动作**：把选定方法用于各组，合计初筛费用和预计阳性设备所需复核分钟数；先不要急着优化复核顺序。
- **目的**：确认候选规则是否同时满足初筛预算和复核容量。
- **成功信号**：结果中分别有“货币单位”和“分钟”，不会把两者直接相加；若容量不足，能算出超过多少分钟或多少台。
- **反思**：若只按PPV从高到低复核，会不会使某一来源组完全得不到服务？

### 入门反思

在继续前，用三句话写下：你的分析单位是什么；PPV的分母是什么；复核容量不足时，你准备比较哪两种分配原则。不要在看到所有结果后才倒推比较规则。

## 标准任务（本课应完成）

1. 对所有“来源组×初筛方法”计算性能、预计流量、费用和损失，并核对单位。
2. 比较至少两个可执行方案。其中一个可以偏向期望损失较小，另一个可保留有理由的最低服务份额。
3. 将未复核阳性中预计存在的故障计入漏检；不要只计算初筛阶段的假阴性。
4. 在低、基准、高基础率下重算容量溢出、预计漏检和总损失，并说明换方案条件。
5. 在`report.md`中区分历史验证结果、规划假设和行动建议，给出工作人员能够照着执行的顺序。

## 提高与拓展（提前完成后）

- 对敏感度或特异度下降设置情境，检查方案对性能迁移失败是否稳健。
- 比较“每台复核带来的期望损失减少量”与单纯按PPV排序，解释两者为何可能不同。
- 把最低服务份额从一个值改为一组合理范围，展示公平服务与总期望损失的取舍曲线。
- 若要串联两种初筛，先说明缺少联合验证数据导致什么不可识别，避免直接相乘边际准确度。

## 卡住时按顺序排查

1. 先用`pwd`确认位于仓库根目录，再运行`python scripts/course.py run 09`。
2. 找不到字段时，对照`data/inference/README.md`和概览中的`columns`，不要凭印象改列名。
3. 概率不在0到1之间时，先检查分子、分母是否放反，以及百分数是否又除了一次100。
4. 台数对不上时，逐组核对“真阳性+假阳性=全部阳性”，再合计。
5. 容量对不上时，检查你合计的是台数还是分钟，并确认每组`review_minutes`。
6. 报告写不下去时，先回答“推荐哪套规则、依据哪张表、哪种情境会换规则”三个问题。
