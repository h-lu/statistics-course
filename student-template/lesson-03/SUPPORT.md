# 第3课支持路线：从“数据有问题”走到“这份数据能不能用”

如果你不知道从哪里开始，按下面顺序做。每一步都写了四件事：现在做什么、为什么做、怎样算完成、完成后问自己什么。基础练习只是可信起点，之后仍要完成标准任务；提高与拓展只供已经完成标准任务的同学继续检查。

## 先知道今天要交出什么

至少留下四类东西：

1. `report.md`：说明使用者、用途、记录范围、方法、结果和建议；
2. `analysis.py` 或其他可运行程序：能够从原始数据重新生成结果；
3. `artifacts/` 中的处理后数据、问题标记和核对结果；
4. `submission.json`：正确填写报告、结果文件、运行命令，并在真正完成后改为 `complete`。

## 核心概念与原理

- **分析单位**：结论针对的对象。本课可以按工单或窗口分析；它会决定去重方式和分母。
- **缺失值**：本来需要的信息没有取得。空白、`999`、`-1`等特殊编码要按数据说明判断；缺失不等于0。
- **重复记录与修订记录**：完全相同的行可能是重复导出；同一工单的不同版本是信息更新，不能看到编号重复就全部删除。
- **数据适用性**：数据能否支持某个用途。一个字段缺失，不一定让整张工单对所有用途都无效。

清洗数据的原理不是“删掉看起来不正常的行”，而是保留原始记录和处理原因，再针对具体用途选择纳入记录。这样读者才知道结论覆盖谁、排除了谁。

## 基础练习（可信起点）：入门跟做

### 1. 先不用电脑，判断三件事

在 `report.md` 写下你的答案：

- `ticket_id` 出现三行，是否一定代表三张工单？
- 等待值为 `999`，能否先除以60？
- `window_id` 为空，能否归到某个中心？

**正确方向**：编号重复要看是否是完全重复或不同版本；`999` 是未测量编码，不能换算；空窗口只能保留为未知。

**反思**：你以前是否把“有数字”误当成“有有效信息”？字段的含义比单元格的外观重要在哪里？

### 2. 运行起点，先不要改代码

在仓库根目录运行：

```bash
python scripts/course.py start 03
python scripts/course.py run 03
```

打开 `lesson-03/artifacts/starting_overview.json`，再看 `data/service/tickets_raw.csv` 的表头和数据说明。把下面五个量记在草稿中：原始行数、非空工单编号数、修订版本数、等待单位、特殊缺失编码数。

**为什么**：原始行数不等于工单数；不同单位也不能直接比较。先认识原始结构，后面才能解释处理后数量。

**成功信号**：你能用完整句子解释“原始有多少行”“不同工单有多少张”“哪些计数还没有经过版本处理”。

**反思**：如果原始表中45行单位为秒，为什么不能直接说有45张工单需要换算？

### 3. 用五行学习例子练习版本和单位

先读 `LEARN.md` 的五行例子，再自己回答：5行最后保留几张工单？R2的办结状态能不能用？等待均值的分母是3还是2？

核对过程：R1的两个版本先保留版本2，180秒换成3分钟；R1还有一行完全重复；R2的999是未知等待但办结状态仍可用于办结比例；R3的60分钟是真实值，不能因为很大就删除。

**反思**：如果最新版本的等待是999，你会不会擅自用旧版本补上？除非有明确来源和规则，否则应保留“未知”，不能为了得到完整表而猜值。

## 入门反思

任选一张学习例子中的工单，说明采用哪一版、等待值是否有效、它能参加哪个指标。再问自己：同一张工单为何可能适合一个用途，却不适合另一个用途？

## 标准任务（本课应完成）

### 4. 选择两个用途，但先检查字段够不够

现在才打开 `report.md`，选择至少两个用途。为每个用途填写这个小表：

| 用途 | 分析单位 | 需要的字段 | 纳入条件 | 分子/分母 | 能支持的决定 |
|---|---|---|---|---|---|
| 例：办结比例 | 工单 | `completed` | 办结状态已知 | 办结工单数/状态已知工单数 | 是否需要核查办结流程 |

**为什么**：先看字段再选用途，可以避免承诺一个数据根本无法回答的问题。

**成功信号**：每个比例都有分母；你能解释等待缺失但办结已知的工单为什么可以只参加办结比例。

**反思**：如果要求所有指标都用同一批完整工单，结果会更容易比较，但会不会排除本来能用于某个单独指标的记录？

### 5. 写处理记录，不覆盖原始数据

按这个顺序修改程序：完全重复 → 选择最新版本 → 识别缺失编码 → 统一单位 → 核对代码。输出至少包含原始值、处理后值、问题标记和处理原因，保存到 `lesson-03/artifacts/`。

运行：

```bash
python scripts/course.py run 03
python scripts/course.py check 03
```

**成功信号**：随机挑一张工单，你能说出它采用了哪个版本、等待值是否换算、是否参加每个指标，以及没有参加的原因。

**反思**：问题数量之和为什么可能大于“有问题的工单数”？一张工单同时有未知窗口和缺失等待时，应该计几张有问题的工单？

### 完成标准任务的判断

完成 README 的四项任务：至少两个用途、可重复处理程序、一个有实际结果的替代处理比较、每个用途的建议。报告必须区分：

- 按给定约定处理的记录；
- 有外部证据才可以修正的记录；
- 仍然未知、不能用于当前用途的记录。

## 提高与拓展（提前完成后）

完成标准任务后，从 README 的四项提高任务中任选一项：

- 做“处理链抽查”时，抽样要覆盖不同处理类型，不能只抽没有问题的记录。核对表至少列出 `ticket_id`、原始行、采用版本、原值、处理值、问题标记和参加的指标；
- 做“记录选择敏感性”时，两种方案使用相同指标定义，只改变记录范围。除结果外，还要报告覆盖工单数和覆盖比例，并检查被排除记录是否集中在某类业务或窗口；
- 做“故障测试”时，微型输入应与正式数据分开保存。程序应把冲突或无效值明确标记、隔离或停止处理，不能默认采用文件最后一行；
- 做“核实优先级”时，说明每类待核实记录会影响哪个分母或建议。优先级来自对决策的影响，不只来自缺失数量。

完成后在报告中写清：新增检查发现了什么，标准任务的处理规则是否需要修改，原来的数据使用建议是保留、增加条件还是改变。

## 卡住时按顺序排查

先确认仓库根目录，再确认字段名和数据说明；保留完整报错；数字不一致时先检查版本筛选、单位换算和分母；不要手改JSON或结果表来对齐示例。报告不会写时，先填“用途—需要的信息—处理规则—结果—限制—建议”。
