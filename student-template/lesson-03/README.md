# 第3课 · 业务数据质量与适用性评估

本课使用**教学合成数据**，即为学习而生成的数据，不是真实机构或个人的记录。你可以全程使用AI帮助理解概念、编程、分析和写作，但提交前要核对结果和结论。

第一次使用这些资料时，可先看[阅读材料与运行程序的小指南](../docs/READING_GUIDE.md)。

如果你不知道下一步做什么，打开本课的[支持路线](SUPPORT.md)，按“入门跟做”逐项完成，再选择标准或提高任务。

## 项目背景

新一期工单导出时出现了重复行、不同修订版本、秒与分钟混用，以及表示未测量的特殊编码。管理者需要判断：这些数据能否用于等待时间、当日办结或窗口工单数量报告？

本课不是把所有空白填满，而是判断哪些记录适合回答哪种问题。窗口工单数量只能描述登记业务量，不能直接表示实际劳动时间或个人效率。

## 先读哪些文件

先读[知识准备](LEARN.md)并尝试其中的小例子，再核对[服务数据说明](../data/service/README.md)。正式项目主要使用以下三个文件，路径从学生仓库根目录写起：

| 文件 | 用途 |
|---|---|
| `data/service/tickets_raw.csv` | 2026年4月13日至24日的第二期导出，1,265行、1,200个工单编号 |
| `data/service/windows.csv` | 根据 `window_id` 查窗口及所属中心 |
| `data/service/business_types.csv` | 根据 `business_code` 核对业务类型 |

窗口和业务表是代码说明表，不是新的工单。第一期 `tickets.csv` 与第二期没有相同工单，不可用第一期记录补出第二期的未知真值。本课不要求同时完成第8课的七表整合。

同一工单的 `export_revision` 数值越大，版本越新；同版本完全相同的行是重复导出。等待值999与−1表示未测量，应先识别，再按 `wait_unit` 统一秒和分钟。未知窗口、空业务和空办结结果要保留为待核实信息，不能猜填。

## 分析任务

1. **选择至少两个用途。** 说明按什么对象分析、需要哪些信息、纳入哪些工单，以及每个比例的分子和分母。例如，描述已服务工单等待时，需要有效等待及明确未放弃的状态；计算办结状态已知工单中的办结比例，只需有效办结状态；统计各窗口工单数，需要能查到窗口归属。可以选其他有依据的用途。
2. **编写可重复运行的处理程序。** 先识别完全重复行，再按数值版本选择最新记录，然后识别缺失编码、核对单位和取值。核对原始行数、不同工单数、重复行、被替代的旧版本行、单位换算和各类问题数量。保留原文件和原字段，把处理后的表及处理原因另存到 `artifacts/`。
3. **比较一种合理的替代处理。** 至少选一个指标，实际比较两种有理由的记录选择或处理方法。例如，为办结比例只要求办结状态有效；另为多个指标共用记录，同时要求等待、办结和窗口信息有效。说明这种选择的用途、两种分母和结果是否不同、使用建议是否需要改变。也可比较有依据的插补与不插补；不要求必须插补或出现结果反转。已知的版本、缺失编码和单位换算规则不能任意改动。
4. **对每个用途提出使用建议。** 写明可以使用、只描述部分范围，还是需要先核实。区分“按已有约定处理”“有额外来源证据支持的修正”和“仍未知”；没有核实来源时，不要求编造已查实的修正。

## 处理记录应让别人看懂什么

报告和结果应能追溯某张工单采用了哪一版，原值与处理后值是什么，哪些问题仍存在，以及它参与了哪些指标。可以在处理后的表增加列，或另外保存核对表；没有固定文件数量或指定软件要求。

行数核对可写成“原始行数＝最终不同工单数＋完全重复行数＋被替代的非重复旧版本行数”。一张工单可能有多种问题，问题次数之和不等于有问题的不同工单数。未参与某个指标的工单仍要保留，不要只导出一张删光所有缺失的表。

长等待不自动等于错误；未知放弃状态不等于已服务。完整案例分析是按本次所需字段选择没有缺失的记录，不是一律检查表中所有字段；还需先核查代码、单位和取值是否合法。遇到最新版本冲突时，停止自动选值并保留问题。两期均值之差不能直接解释为清洗的效果。

## 需要提交什么

提交 `report.md`、处理程序、处理后的数据和核对结果。报告至少包含两个用途，以及一项有实际结果的替代处理比较。每个用途要对应“所需信息、处理规则、参与计算的记录、指标与使用建议”；说明继续核实哪些记录可能改变建议。

第3课开始按既有规则记录完成分；正确率不直接计分。是否评代表作品质量取决于模块末的作品选择，详见[成果与评分](../docs/ASSESSMENT.md)。

## 示例运行后，接下来做什么

初次运行生成 `artifacts/starting_overview.json`。JSON是按字段名保存结果的文本格式，可用编辑器打开；终端打印的是文件位置，不是完整分析报告。

`raw_rows` 是原始行数，`unique_ticket_ids` 是不同的非空工单编号数，`blank_ticket_id_rows` 单列编号空白的行；`wait_units` 和 `revision_counts` 分别数原始行中的单位与版本，`missing_wait_code_rows` 只数原文为999、−1这两种编码，不是全部缺失或无效记录数。

这些计数尚未处理重复与修订。例如原始表中有45行标为秒，不意味着处理后要转换45张工单。请先选择每张工单的最新记录，再统计真正完成换算的数量。若两项计数恰好相同，也不能据此认定它们一直描述同一批记录。

按上面的任务扩展程序；仅提交这个概览还没有完成作业。

## 运行与提交

在自己的学生仓库根目录运行，即包含 `scripts/` 和 `data/` 的文件夹。使用完整课程资料库时先进入 `student-template/`。

```bash
python scripts/course.py start 03
python scripts/course.py run 03
```

根据任务修改或替换 `analysis.py`，将结果保存在本课 `artifacts/`，并在报告中解释和引用。原始数据保持不变；使用的新软件包写入 `requirements.txt`。

完成后，在 `submission.json` 将 `status` 改为 `complete`，填写 `report`、结果文件列表 `artifacts` 和运行命令 `run`。这些路径从学生仓库根目录写起，更换程序时也要更新命令。重新运行并检查：

```bash
python scripts/course.py run 03
python scripts/course.py check 03
```

**`run` 执行程序；`check` 只检查完成状态、路径和文件是否存在且非空，不会重新运行分析，也不判断统计结论。** 按[操作与提交步骤](../docs/WORKFLOW.md)提交并推送，创建最终标签 `v2-l03-final`，查看自动检查结果。自动检查能核对程序能否重新生成所列结果，不能替代对分母和结论的判断。

已有最终标签不要覆盖。遇到网络、环境或检查失败，保存本地文件和提交并向教师说明；详细命令和修订办法见上述操作说明。

最后约15分钟进入[知识自查](https://hblu.top/stat-check/)，确认页面为第3课。建议先完成A题，学习不熟悉的概念，再完成B题并阅读反馈。AI始终可用，不要求提交对话；正确率用于反馈，不直接计分。详见[知识自查说明](../docs/KNOWLEDGE_CHECK.md)。
