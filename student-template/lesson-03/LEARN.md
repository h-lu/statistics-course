# 第03课 · 一条记录缺了等待时间，还能用吗？

一张工单没有等待时间，但清楚记录了已经办结。计算平均等待时，它不能参加；计算办结比例时，却不一定要丢掉。

所以，整理数据不能只按“有空白就删整行”。本课先判断每条记录是哪张工单、哪个版本，再按要回答的问题选择有效信息。下面会用五行导出记录算出两个不同分母的结果。

## 先记住三个问题

看到一列数据，先问：

1. 这一行描述的对象是谁？
2. 这个值的含义、单位和有效范围是什么？
3. 我准备计算的指标，分母到底包括哪些记录？

代码可以帮助计算，但不能替你回答这三个问题。

## 1. 观测单位、分析单位和版本

**观测单位（observational unit）**是记录描述的对象，这里是工单。但原始文件里，同一张工单可能被导出多次，出现多行。

我们想按工单作结论，所以**分析单位（unit of analysis）**仍是工单。比如同一位来访者办了两张不同工单，应算两张；同一张工单导出三次，却不能当成三张。先分清这两种重复，再处理文件。

**变量（variable）**是为对象记录的属性。等待时间是数值变量，可以在单位一致时计算均值；窗口和业务类别是分类变量，编号中的数字不表示大小。放弃状态虽然用0和1编码，表示的仍是“否”和“是”两个类别。

**主键（primary key）**是能够唯一识别一条记录的字段或字段组合。整理后的工单表可以用 `ticket_id` 作主键，但原始导出中同一个编号可能出现多行，所以必须先检查它们为什么重复。

- **完全重复记录（exact duplicate）**：字段内容完全相同，常见原因是同一行被重复导出；
- **修订记录（revised record）**：同一工单的信息后来更新，`export_revision` 数值更大的版本更新；
- **冲突记录（conflicting record）**：同一最新版本出现不同内容，不能不作说明就选择其中一行。

文件排在后面不代表版本更新。先按版本号判断，再处理重复和冲突。

## 2. 缺失、无效和离群值不是一回事

**缺失值（missing value）**表示所需信息没有取得。本课等待值 `999` 和 `-1` 是未测量编码；`0` 是已测得的零等待，不是缺失。处理时分三步：先识别缺失编码，再检查单位，最后换算有效数值。例如180秒可换成3分钟；999是本课约定的缺失编码，不能算成16.65分钟。

**无效取值（invalid value）**不符合字段定义。例如状态代码不在数据说明允许的范围内，或者单位名称无法识别。它应被标记为问题，不要猜成某个合法类别。

**离群值（outlier）**是与多数记录明显不同的值。60分钟可能很长，但仍可能是真实等待。只有“数值很大”不能成为删除理由；应核对来源，并报告它对结果的影响。

有些空白是因为字段不适用。放弃排队的工单没有面对面服务时长，不代表服务时长为0。先理解字段，再判断空白。

## 3. 先判断，再计算五行例子

下面是另设的学习例子，不是正式项目数据。办结状态1表示当日办结，0表示未当日办结；`UNKNOWN`表示窗口未知。

| 工单 | 版本 | 原等待值 | 单位 | 当日办结 | 窗口 |
|---|---:|---:|---|---:|---|
| R1 | 1 | 120 | 秒 | 1 | A1 |
| R1 | 1 | 120 | 秒 | 1 | A1 |
| R1 | 2 | 180 | 秒 | 1 | A1 |
| R2 | 1 | 999 | 秒 | 1 | UNKNOWN |
| R3 | 1 | 60 | 分钟 | 0 | A1 |

先不要看答案，写下：应保留几张工单？R2能不能参加办结比例？等待均值的分母是3还是2？

再按顺序核对：

1. R1的两行版本1完全相同，一行是重复导出；版本2是更新版本；
2. 最终保留R1、R2、R3，共3张工单；
3. R1等待为180÷60=3分钟；R2等待未知；R3等待为60分钟；
4. R2的办结状态已知，可以参加办结比例，但不能参加等待均值。

整理后的三张工单如下。空白仍保留为未知，不补成0。

| 工单 | 等待分钟数 | 当日办结 | 窗口 |
|---|---:|---:|---|
| R1（版本2） | 3 | 1 | A1 |
| R2 | 未知 | 1 | 未知 |
| R3 | 60 | 0 | A1 |

分别计算指标：

| 指标 | 参加的工单 | 计算 | 结果 |
|---|---|---|---:|
| 有效等待的算术平均数（简称均值） | R1、R3 | (3+60)/2 | 31.5分钟 |
| 办结状态已知时的办结比例 | R1、R2、R3 | 2/3 | 约66.7% |
| 已确认属于A1的工单数 | R1、R3 | 计数 | 2张 |

31.5分钟只描述两张有有效等待的工单，不是三张工单的完整平均值。A1的“已确认2张”也不等于A1全部只有2张，因为R2的窗口未知。

下面代码的输入是整理后的R1、R2、R3，不是原始五行。它没有自动替你处理版本，只复算整理后的指标。

代码用 `None` 表示未知。先看 `waits`：只收集两条有效等待，所以 `wait_n` 应为2，`wait_mean` 应为31.5。再看 `completion_rows`：三条办结状态都已知，所以 `completion_rate` 应为2/3。结果打印在终端。增加一个无关的空白备注，不应改变这些分母。

```python
# learning-example
import json


rows = [
    {"ticket_id": "R1", "wait": 3, "completed": 1, "window": "A1"},
    {"ticket_id": "R2", "wait": None, "completed": 1, "window": None},
    {"ticket_id": "R3", "wait": 60, "completed": 0, "window": "A1"},
]

waits = [row["wait"] for row in rows if row["wait"] is not None]
completion_rows = [row for row in rows if row["completed"] is not None]
complete_case_rows = [
    row for row in rows
    if all(row[field] is not None for field in ("wait", "completed", "window"))
]

result = {
    "target_n": len(rows),
    "wait_n": len(waits),
    "wait_mean": sum(waits) / len(waits),
    "completion_rate": sum(row["completed"] for row in completion_rows) / len(completion_rows),
    "complete_case_rate": sum(row["completed"] for row in complete_case_rows) / len(complete_case_rows),
    "known_window_n": sum(row["window"] is not None for row in rows),
}
print(json.dumps(result, ensure_ascii=False, sort_keys=True))
```

## 4. 为什么同一批数据会有不同分母

**完整案例分析（complete-case analysis）**是只使用**本次分析所需字段**都有效的记录进行分析的方法，不是要求表中所有字段都必须有值。分析问题不同，所需字段也可能不同，因此“完整”必须跟具体用途一起说明。

只计算办结比例时，三张工单的办结状态都已知，结果是2/3。若另一个报告要求等待、办结和窗口三项都有效，那么R2会被排除，办结比例变为1/2=50%。

50%和66.7%的差别来自纳入记录不同，并不表示真实办结情况被清洗程序改变。这里，要求更多字段有效，改变了参与计算的工单范围。

可以分别按每项指标所需字段选择完整记录，也可以统一使用等待、办结和窗口都完整的记录。前者保留更多可用信息；后者便于多个指标在同一批工单上比较，但会排除本来能参加单项计算的记录。报告应说明采用哪种方案及其取舍。

上面程序中的英文字段对应以下含义；比例使用0到1表示，例如 `completion_rate` 的约0.667就是约66.7%。

| 输出字段 | 中文含义 |
|---|---|
| `target_n` | 整理后不同工单数，本例为3张 |
| `wait_n`、`wait_mean` | 有效等待的工单数，以及这些工单的平均等待分钟数 |
| `completion_rate` | 办结状态已知工单的当日办结比例 |
| `complete_case_rate` | 等待、办结和窗口都完整的工单的当日办结比例 |
| `known_window_n` | 窗口已知的工单数 |

**插补（imputation）**是利用已有资料和假设，为缺失值补入估计值。插补值不是查实的原值。本课不要求插补；如果选择插补，必须保留原值和插补标记，并比较插补与不插补的结果。

## 5. 两个自测问题

**问题一：** 10张不同工单中，3张缺等待，2张窗口未知，其中1张同时缺等待且窗口未知。有问题的不同工单有几张？

**问题二：** 一张工单等待12分钟，但是否放弃未知。它能否进入“已服务工单平均等待”？如果所有工单都没有有效等待，平均值应写0吗？

## 怎样完成本课

- **基础完成：**把五行例子整理成三张工单，手算等待均值与办结比例，说明R2为什么能参加一个、不能参加另一个。
- **完整完成：**按[任务页](README.md)为至少两个用途写清所需字段与纳入条件，并实际比较一种有理由的记录选择。保存原始记录、处理结果和原因，不能只留下“干净表”。
- **扩展练习（选做）：**在保持办结状态不变的情况下，给一张工单加一个无关空备注。预计各指标是否应变，再用程序检查；若改变了，定位代码中多余的过滤条件。

## 回到项目

为至少两个用途填写：分析单位、所需字段、纳入条件、指标、分子、分母和建议。至少一个指标要实际比较两种有理由的记录选择。排除某项计算不等于删除原文件；原始数据保留，处理结果和原因另存。

已给定的版本优先、缺失编码和单位换算规则不能随意修改。没有外部核实来源时，写“按约定处理”或“仍未知”，不要写“已经找到真实值”。两期日期不同，两期均值之差也不能直接解释为清洗或管理改善。

## 再进一步：全部工单的比例可以在哪个范围？

另设5张工单：3张已办结、1张未办结、1张办结未知。状态已知者的办结比例是3/4=75%，分母是4张。若问题改为全部5张的办结比例，未知者未办结时为3/5=60%，未知者已办结时为4/5=80%。因此现有资料只能把全部比例限制在60%—80%；75%不能自动作为全体已测得的比例。

若有 `s` 张已知办结、`u` 张状态未知、总计 `N` 张不同工单，逻辑下界是 `s/N`，上界是 `(s+u)/N`。分子是办结工单数，分母是全部登记工单，结果单位是比例；这里判断的是同一个观察日结束时是否办结，每张工单的真实状态只能是两者之一。当天未办结的工单以后可能办结，但那是另一个时间点的问题。这是缺失真值的可能范围，**不是置信区间（confidence interval）**，也没有处理未登记者或错误测量。

回到第二期时，先明确你要描述状态已知者还是全部登记工单，才决定报告哪一种结果。范围较窄不代表没有其他数据质量问题。

## 独立练习：五个概念及其迁移

先独立写计算和理由，再用本页定义复核。可以请AI换一个情境追问；这些练习不替代标准项目，也不修改线上题目。

1. **分析单位与版本：**一位来访者有P、Q两张工单；P有版本2与10各一行。应保留几张工单，P采用哪版？变式：若最高版10有两行不同内容，你需要补充哪种证据或处置规则？
2. **缺失、单位与零：**0秒、120秒、999秒、−1分钟四条等待记录，哪些有有效等待？有效值的均值与分母是什么？变式：把120的单位改为未知，你还可以算原来同一目标的均值吗？
3. **问题重叠：**12张工单中4张缺等待、3张窗口未知，2张同时如此。至少有一个问题的工单有几张？变式：另有1张办结未知但没有前两种问题，问题标记次数与有问题的工单数各怎样变化？
4. **所需字段：**4张工单的办结状态是1、1、0、未知；第二张窗口未知，其他窗口已知。只要求办结状态已知的办结比例，与同时要求办结状态和窗口已知的办结比例，分母各有几张？变式：增加一个无关的空备注列，会改变这些结果吗，为什么？
5. **离群值与适用范围：**已服务工单等待2、3、55分钟，没有来源证据说55错误。你会怎样核对并报告？变式：55改为−55但数据定义为非负时，处理理由为何不同？

核对时特别看：版本按数值，不按字符串；缺失在单位换算前识别；重叠只数一次；字段要求由用途决定；长等待与违反定义的值分别处理。可以用自己的短例子或AI换题再检验理解，不必等待统一讲解。

## 按需了解：遇到最新版本冲突

如果同一工单的最新版本内容不同，应保留冲突并停止自动选值，或把该工单单列后继续不受影响且范围明确的分析。不能自行平均、猜选或用文件最后一行代替版本规则。
