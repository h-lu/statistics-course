# 设备告警数据：教学合成数据

本目录中的数据由程序按固定设置生成，不包含真实设备或真实损失。生成脚本是 `scripts/generate_alerts.py`，其中随机种子 `26090505` 用来保证每次生成相同的数据。这组数据用于比较不同复核规则的成本与损失，金额和复核效果属于教学情境中的给定假设。

## 项目背景

维护团队每天收到90台设备的**风险分数**，也就是系统给出的相对风险排序信息。工作日最多复核20台，周末最多15台；这个每日上限称为复核容量。不同设备的故障损失不同，复核也有成本。任务是给出可以按日期执行的名单，不能把“分数高”直接等同于“故障概率高”或“最值得复核”。

**观测单位**是数据中每行所记录的对象。`development.csv` 和 `evaluation.csv` 的观测单位都是设备日，即某台设备在某一天的一次判断机会；`devices.csv` 的观测单位是设备；`daily_capacity.csv` 的观测单位是日期。

| 文件 | 行数与观测单位 | 字段 |
|---|---|---|
| `development.csv` | 3,780条，42天×90台；每台设备每天一行 | `record_id`为每条记录的唯一编号，`date`为日期，`device_id`为设备编号，`risk_score`为0—100分的风险分数，`failure_within_24h`表示随后24小时内是否故障（0/1） |
| `evaluation.csv` | 1,260条，之后14天×90台，字段同上 | 时间顺序晚于规则制定期；用于规则确定后的留出评价 |
| `devices.csv` | 90台，每台设备一行 | `device_id`为每台设备的唯一编号，`campus`为校区，`device_class`为设备类别，`miss_loss`为一次故障损失，`inspection_cost`为一次复核成本，`prevention_fraction`为复核能避免的故障损失比例 |
| `daily_capacity.csv` | 56天，每天一行 | `date`为该行对应的唯一日期，`batch`为所属时期，`max_reviews`为当天最多复核数 |

损失与成本统一以“教学成本单位”计量，不是真实人民币报价。分数只是排序信号，`risk_score=70`不表示70%故障概率。

## 复核后果的计算约定

为了比较规则，本模拟假设每台被复核设备都支付复核成本；如它原本会故障，可避免85%的故障损失，其余15%仍发生。未复核的故障承担全部损失。不复核且不故障不产生损失。可少用名额，不能超过当日容量。

因而一条记录的情境损失为：

- 未复核：故障标记×故障损失；
- 已复核：复核成本＋故障标记×故障损失×(1−可避免比例)。

这些是给定的决策假设，不能从历史数据评价中声称“已经证实复核具有85%的因果效果”。**因果效果**是采取复核相较于不复核造成的结果变化；仅根据这组历史记录和给定假设不能证明这种变化。可以通过敏感性分析改变效果假设，观察决定是否改变。

## 时间与结果变量

这里的**结果变量**是 `failure_within_24h`，表示设备随后24小时内是否故障。所有历史记录都经过统一追踪，因此每条记录都有这个结果；不存在“只有被复核者才知道结果”的缺失。生成当天名单时，只能使用行动当时已知的分数、设备信息与既往数据，不能用当天尚未发生的故障结果排序。先用前42天的规则制定期提出并选择规则，再用保留的后14天进行留出评价。若看过后14天后再修改规则，应标明为探索性修订，并使用新数据评价修改后的规则。

两个时期包含相同设备，但日期不同，数据中可能存在时期变化。同一设备不同日期的记录也可能相互关联，因此不能假定所有设备日彼此独立。14天评价结果只能支持在已说明条件下的试运行建议，不能保证未来损失相同。
