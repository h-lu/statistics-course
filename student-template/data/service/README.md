# 服务中心数据说明

本目录中的数据都是**教学合成数据**：使用固定随机种子 `26090501` 生成，只用于练习统计分析，不代表真实学校、企业、工作人员或来访者。A、B、C 三个中心和所有编号均为虚构。

生成程序是 `scripts/generate_service.py`。它说明了本练习的模拟情境，但不能证明现实中的服务一定按照相同方式发生。

## 先用一句话理解这些数据

这里有三类不同问题：

1. **工单发生了什么？** 例如等待多久、是否放弃、是否当日办结；
2. **来访者怎样评价？** 例如是否被邀请、是否回答、评分是多少；
3. **服务过程怎样进行？** 例如一张工单有几次接触、计划安排多少人时。

这些问题的记录单位不同，不能把所有表直接拼在一起，也不能把等待、满意度和工作量自动合成一个总分。先确定问题，再选择需要的表。

## 数据范围和每张表代表什么

| 文件 | 时间和规模 | 一行代表什么 | 适合先回答什么 |
|---|---|---|---|
| `tickets.csv` | 2026-03-02 至 2026-04-10；3,600行 | 一张已整理的登记工单 | 登记量、等待、放弃、办结 |
| `tickets_raw.csv` | 2026-04-13 至 2026-04-24；1,265行、1,200个工单编号 | 一行原始导出记录；同一工单可能多行 | 检查重复、修订、单位和特殊编码 |
| `satisfaction.csv` | 两期合计4,800张工单 | 一张调查登记 | 邀请、回答和满意度评分 |
| `visits.csv` | 8,921行 | 一次服务接触 | 接触次数和工作人员分钟数 |
| `windows.csv` | 6行 | 一个窗口 | 把 `window_id` 对应到中心 |
| `business_types.csv` | 2行 | 一种业务类别 | 把 `business_code` 对应到业务名称和复杂程度 |
| `staffing.csv` | 240行 | 一个窗口在一天的排班 | 计划人数、开放小时和缺勤工时 |

`tickets.csv` 是第一期已经整理好的基础登记，适合第1、2、4课先开始使用。`tickets_raw.csv` 是第二期原始导出，专门用于第3课的数据质量练习；它与第一期没有相同工单，不能用第一期去寻找第二期工单的“正确答案”。

这些记录覆盖模拟期间**已经登记的工单**，不是随机抽取的全校人群，也不包括没有取号的人。第一期和第二期发生在不同时间，两个时期的差异不能直接归因于中心或工作人员。

## 按问题选择数据

| 如果你要回答…… | 主要使用…… | 需要特别说明…… |
|---|---|---|
| 已服务工单通常等多久 | `tickets.csv` 的有效 `wait_minutes` | 放弃者不能当成已服务；写清分母 |
| 有多少工单放弃 | `tickets.csv` 的 `abandoned` | 放弃比例通常以放弃状态已知的登记工单为分母 |
| 哪个中心登记量较多 | `tickets.csv` 加 `windows.csv` | 这是登记业务量，不是人员工作量 |
| 工单是否当日办结 | `completed_same_day` | 这是登记结果，不直接衡量工作努力 |
| 满意度怎样 | `satisfaction.csv` 加 `tickets.csv` | 未受邀与受邀后无回答要分开；评分空白不是0分 |
| 一张工单有几次接触 | `visits.csv` 加 `tickets.csv` | 一张工单可能对应多行接触，直接连接可能重复计数 |
| 计划安排多少人时 | `staffing.csv` | 这是计划量，不是实际劳动时间的完整测量 |

如果只分析第一期，满意度、接触和排班表也必须限定到相同日期或相同工单集合。不要因为两个表都有 `ticket_id` 就直接把所有行连接后求平均。

## 工单表的主要字段

| 字段 | 含义和使用提醒 |
|---|---|
| `ticket_id` | 工单编号。整理后的 `tickets.csv` 中可作为主键；原始导出允许同一编号重复或出现修订版本。 |
| `person_id` | 来访者编号。一个人可以有多张工单，所以按工单分析和按人分析不是同一件事。 |
| `date` | 登记日期。跨时期比较前先明确日期范围。 |
| `arrival_period` | 上午或下午的登记时段。它是分类变量，不是连续的时间长短。 |
| `window_id` | 窗口编号，需要到 `windows.csv` 查所属中心。不能从编号的字母或数字大小推测中心优劣。 |
| `business_code` | 业务代码，需要到 `business_types.csv` 查业务名称和复杂程度。 |
| `appointment` | 是否预约：1表示是，0表示否。 |
| `wait_minutes` | 从开始排队到开始服务，或到放弃离开的等待分钟数。放弃者的数值是离开前等待，不表示已经获得服务。 |
| `service_minutes` | 面对面服务分钟数。放弃者为空，空值不等于完成了0分钟服务。 |
| `abandoned` | 是否放弃排队：1表示是，0表示否。 |
| `completed_same_day` | 是否当日办结：1表示是，0表示否；这是登记结果，不是工作人员努力程度的直接测量。 |

## 原始导出还要检查什么

`tickets_raw.csv` 用于练习数据质量处理，不能直接当成每行一张不同工单：

- `wait_unit` 为 `minute` 时按分钟读；为 `second` 时要先除以60；
- `wait_minutes` 中的 `999` 和 `-1` 是“未取得测量值”的编码，先识别再换算，不能当成999秒或负等待；
- `export_revision` 数值较大的版本较新；不能因为某行排在文件最后就认为它最新；
- 同一版本、所有字段完全相同的行是重复导出；同一最新版本内容冲突时，应保留冲突并待核实；
- `UNKNOWN` 或空白窗口、业务和办结状态不能自行猜测；
- 很大的等待值可能是真实的长等待，不能只因为它是离群值就删除。

处理时保留原始文件，另存处理后的值、问题标记和处理原因。不同指标可以使用不同的有效记录集合，但必须报告每个分母、保留数和排除原因。

## 调查表、接触表和排班表

`satisfaction.csv` 中：

- `invited=0` 表示没有发出邀请；
- `invited=1` 且 `score` 为空，表示受邀后没有回答，即**无回答**；
- `score` 为1—5级体验评价，空白不是中立评价，也不是0分；
- `response_days` 是距邀请的回答天数，未回答时为空。

`visits.csv` 中，一行是一次接触，不是一张工单。`contact_id` 是接触编号，`ticket_id` 连接所属工单，`contact_sequence` 是工单内第几次接触，`staff_minutes` 是该次接触耗用的工作人员分钟数。一张工单有多次接触时，直接把接触表连接到工单表，可能把工单等待重复计算。

`staffing.csv` 中，`date` 和 `window_id` 共同确定一个窗口的一天。`staff_count` 是排班人数，`open_hours` 是每人开放小时，`absence_hours` 是当天合计缺勤工时。计划有效工时按：

```text
人数 × 每人开放小时 − 当天合计缺勤工时
```

`absence_hours` 已经是合计值，不能再乘一次人数；计划有效工时也不等于实际劳动时间。

## 最后检查三个常见误区

1. **把“有数字”当成“有效信息”**：999是缺失编码，60分钟可能是真实长等待；要看字段定义和来源。
2. **把不同分母的比例放在一起比较**：已服务等待和全部登记放弃比例回答不同问题，必须分别写分母。
3. **把统计差异当成因果效果**：中心、业务构成、预约和时间可能同时不同；分组后的差异仍不自动证明工作人员造成结果。

开始一项分析前，先写清楚：我要描述谁、使用哪些记录、指标的分母是什么、这个结果能支持什么决定，以及还缺少什么信息。
