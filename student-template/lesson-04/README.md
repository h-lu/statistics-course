# 第4课 · 设计服务质量评价办法

## 项目背景

服务委员会准备公布月度评价，并据此安排改进工作。只按平均等待排名可能忽略少数人的长等待；只关注中位数可能掩盖尾部；仅按办结率比较又可能奖励更容易的业务。你需要提出一套可解释的评价办法，而不是替指定指标画图。

## 可用数据

使用第一期 `data/service/tickets.csv`、窗口与业务字典，可补充 `satisfaction.csv` 和 `staffing.csv`。参考等待线为常规15分钟、复杂30分钟，是情境参考而非唯一标准。[数据说明](../data/service/README.md)。

本课数据均为教学合成数据，不代表真实机构。先阅读[知识准备](LEARN.md)，再选择分析方法。你可以全程使用AI完成代码、分析和写作；报告需解释主要结论的统计依据、适用条件和局限性。

## 分析任务

为一个明确的使用目标设计服务质量评价制度：说明评价对象、指标含义、发布方式和结果用途。用实际数据展示采用该办法会得到什么结论，并比较另一套目标或指标选择不同的合理评价办法。解释可能产生的不合理激励，给出防护或改进条件。

### 必须遵守的约束

- 可以采用多指标面板而不合成总分；若合成，必须说明方向、量纲、权重和不可替代的底线。
- 必须同时处理日常表现与尾部体验，不能用一个中心位置统计量代表全部分布。
- 保留放弃、业务构成、样本量等影响解读的信息，不能只发布光秃秃的名次。
- 对真实长等待、业务混合或指标权重至少选择一个与制度相关的敏感性问题。
- 本课评价是描述与制度设计，不将排序解释为工作人员的因果贡献。

### 由你决定

使用者可为窗口改进组、服务体验委员会或资源安排组。你决定是发布等级、图表、达标情况还是排名；指标与权重应服务该目标，而非为了使某中心排第一。

## 成果要求

- 给出一页可执行评价规则和按该规则计算的结果，含指标单位、方向和分母。
- 比较替代制度的后果：哪些评价改变、为什么、使用者应如何取舍。
- 明确一个潜在激励问题，例如拒接复杂业务或忽视未获服务者，并提出能执行的防护办法。
- 报告中的关键数值与敏感性分析结果都能重新计算；不要求制作网页或交互界面。

在本目录的 `report.md` 中撰写分析报告，篇幅与结构可按问题需要调整。关键表、图或分析数据保存到 `artifacts/`，并在报告中引用。可以修改或替换 `analysis.py`；提供的示例代码只生成数据概览，不是本课的完整分析。

## 建议时间安排

0—12分钟知识与目标辨析；12—24分钟提出制度草案；24—53分钟计算并比较后果；53—68分钟分析可能的行为激励和局限性，完善评价规则；68—75分钟核对提交；75—90分钟知识自查。复用前课统计量，把主要精力用于制度取舍。

## 运行与提交

从仓库根目录运行：

```bash
python scripts/course.py start 04
python scripts/course.py run 04
```

完成报告和分析后，在 `submission.json` 填入支持报告结论的结果文件路径，将 `status` 改为 `complete`；如果更换运行入口，同步修改 `run`。运行 `python scripts/course.py check 04`，核对修改后提交并创建最终标签 `v2-l04-final`。完整步骤见[操作与提交步骤](../docs/WORKFLOW.md)。自动检查通过只说明文件、路径和运行命令符合提交要求，不代表统计结论正确。

最后约15分钟进入[知识自查](https://hblu.top/stat-check/)，确认页面显示当日第4课，按当前场次作答。建议先自行判断，不会时请AI解释概念再作答；使用方式见[自查说明](../docs/KNOWLEDGE_CHECK.md)。
