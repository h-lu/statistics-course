# 第4课 · 设计服务质量评价办法

**以下数据全部为教学合成数据，不代表真实机构、个人或实际效果。** 可以全程使用AI提出候选问题、编程、分析、写作和协助提交；你需要确认最终采用的选择，核对结果、依据和适用范围。无需提交AI对话或证明代码由谁输入。先阅读[知识准备](LEARN.md)，再展开正式分析。

## 项目背景

服务委员会要公布评价并安排改进。只看平均等待可能忽略日常或尾部体验；只看办结率又可能混入业务构成。你要为明确的使用者设计一套可以照算的评价办法，并解释它会保留和遗漏什么。

## 可用数据

使用第一期 `data/service/tickets.csv`、窗口与业务字典，可按需补充满意度和排班资料。见[服务数据说明](../data/service/README.md)。常规15分钟、复杂30分钟是情境参考等待线，不是统计学规定的唯一标准；选择其他阈值或规则要说明用途与依据。

## 分析任务

1. **把目标写在规则前。** 明确评价对象、结果用途和发布方式，可以使用多指标面板、等级或有条件的排名，不要求总分。
2. **定义并计算规则。** 同时处理日常表现与尾部体验；每个指标说明单位、方向、分子、分母、缺失处理和阈值是否包含等号。保留放弃、业务构成和样本量信息，不能只给名次。
3. **比较另一套合理制度。** 用相同声明范围的数据展示哪些结果改变、为什么改变、使用者如何取舍。至少检查一个与真实长等待、业务混合或指标权重有关的敏感性问题；制度比较与敏感性可共用同一组实质结果，不必重复制作。
4. **提出防护与更新条件。** 说明可能的激励风险，如忽视未获服务者或排除复杂记录，并提出能核查的记录、复核或撤回条件。风险推测不能写成数据已证明有人这样做。

## 必须说明的选择

合成总分时，说明尺度转换、好坏方向、权重及不可补偿的底线；分钟和比例不能未经定义直接相加。按不同业务设置等待线是目标约定，不等于把各中心业务构成都变成相同。

如定义“放弃或超过业务等待线”为不良经历，同一工单即使符合两项也只计一次，并用全体纳入的登记工单作分母。已服务超时比例则以有有效等待的已服务工单为分母。空组或零分母不写成0；精确相同时保留并列，不让名称顺序伪装成优劣。

## 成果与提交前自核

交付一页可执行规则、按规则计算的结果、备选制度和敏感性结果、潜在激励及防护说明。规则可以有条件地暂缓排名，但不能省略实际比较。

进一步完善在于解释哪些目标可补偿、哪些需要单列，并用结果修改适用范围。删除最慢记录后指标改善不证明服务改善；本课是描述与评价设计，不识别工作人员的因果贡献，不按界面或模型复杂度加分。

## 90分钟建议安排

0—12分钟知识与目标辨析；12—24分钟提出规则；24—53分钟计算并比较；53—68分钟核对激励、限制和防护；68—75分钟核对提交；75—90分钟自查。复用前课统计量，把主要精力用于目标取舍。

## 运行、核对与提交

以下“仓库根目录”指你自己的学生仓库中包含 `scripts/`、`data/` 的目录；在合并资料库中阅读时，对应 `student-template/`。先运行：

```bash
python scripts/course.py start 04
python scripts/course.py run 04
```

`analysis.py` 是可运行的数据概览，不是完整项目答案。按问题修改或替换它，将关键数值结果和图表写入本课 `artifacts/`，在 `report.md` 中引用。可以调整报告结构，不能只保留提示或粘贴默认输出。原始数据不改写；新增依赖写入 `requirements.txt`。

完成后，在本课 `submission.json` 中将 `status` 设为 `complete`，填写 `report`、支持结论的 `artifacts` 和非空命令参数列表 `run`。所有路径相对于学生仓库根目录。再执行：

```bash
python scripts/course.py run 04
python scripts/course.py check 04
git diff --check
git status
git diff
git add lesson-04 requirements.txt
git diff --cached
git commit -m "完成第04课项目"
git push
git tag v2-l04-final
git push origin v2-l04-final
```

**`run` 执行分析；`check` 只检查完成声明、路径和文件是否存在且非空，不会重新运行分析或判断结论。** 推送后查看 Actions 的重跑结果；配置了重现检查时，它会在临时副本移除所列结果文件、运行程序并比较内容。固定随机种子、排序和输出精度，避免将带生成时间的文件列入逐字节比较。程序运行成功和文件检查通过，都不等于统计解释正确。

新增共用程序也须核对后纳入提交。已有最终标签不要覆盖；修订保留原版本。网络、环境或检查故障时保存本地文件与提交，向教师说明，不把失败写成已通过。完整步骤见[项目工作流](../docs/WORKFLOW.md)和[成果与评分](../docs/ASSESSMENT.md)。

最后约15分钟进入[知识自查](https://hblu.top/stat-check/)，确认页面为第4课。建议先作答A，再学习不熟悉的概念，完成B并阅读反馈；AI始终可用，无需提交对话记录。自查正确率用于反馈，不直接计分，详见[自查说明](../docs/KNOWLEDGE_CHECK.md)。
