# 第4课支持路线：设计服务质量评价办法

本课从“描述数据”进入“用指标支持决定”。你要为明确的使用者设计一套评价办法，同时保留长等待、放弃和业务构成等信息，不能只给出一个排名。

## 这课到底在学什么

- **集中趋势**：描述数据大致位于哪里，常用均值和中位数。均值更容易受极端长等待影响。
- **离散程度与尾部**：离散程度说明记录相差多大；右尾是等待特别长的一端。一个中心数值可能掩盖尾部。
- **指标**：为某个判断定义的可计算量。必须写清分子、分母、单位、方向和缺失处理。
- **阈值**：触发提醒或行动的界限。“超过15分钟”不包含恰好15分钟，“不少于15分钟”包含15分钟。
- **敏感性分析**：改变一个有理由的指标、阈值或权重，观察评价和建议是否改变。

原理是“评价办法要服务于决定”。统计差异不是工作人员造成效果的自动证明；管理阈值是情境假设，不是统计学定律。

## 入门跟做

### 1. 先写使用者和决定

打开 `lesson-04/report.md`，先写谁会看评价、要决定调查还是改进、允许什么风险。再选两项指标：例如已服务等待的中位数和P90、超过业务参考时间的比例、放弃比例。写明各自分母。

**反思**：如果只报均值，哪些长等待可能被隐藏？如果放弃者不在已服务分母中，放弃比例要另算还是混在等待比例中？

### 2. 运行起点并读字段

```bash
python scripts/course.py start 04
python scripts/course.py run 04
```

打开 `lesson-04/artifacts/starting_overview.json`，确认中心、已服务数、均值、中位数和最大值的单位。再回到数据说明核对业务参考时间和放弃字段。

**做对的信号**：你能指出哪个数字描述位置、哪个数字描述极端值，并知道它们不是同一个指标。

**反思**：最大值只告诉你最慢的一张工单，能不能代表大多数工单？为什么还需要P90或超时比例？

### 3. 手算一个指标

三张已服务工单等待2、4、10分钟：均值为5.33，中位数为4；若阈值是5分钟，“超过5分钟”的比例为1/3。若规则改成“不少于5分钟”，分子会变成2，比例是2/3。

**为什么**：一个等号就可能改变行动数量，报告必须写清阈值方向。

**反思**：两个指标数值相同，是否一定有相同分母？如果不写分母，读者能复算吗？

### 4. 比较评价办法并提出建议

在 `analysis.py` 中实现一套主办法，再选择一项合理替代：改阈值、改中心统计量、分业务比较或改变指标权重。实际运行两套结果，报告列出变化及原因。保留放弃数量和业务构成，不为了排名删除复杂业务。

运行并检查：

```bash
python scripts/course.py run 04
python scripts/course.py check 04
```

**做对的信号**：建议能回答“何时调查、何时试运行、何时暂缓”，而不是只说哪个中心第一。

**反思**：如果两套办法排名相同，是否说明服务全面合格？如果排名改变，改变来自业务构成、指标定义还是阈值？


## 标准完成

在入门路线基础上，完成 README 中全部必做任务：实际比较一个有理由的替代方案，列出每种方案的记录范围、指标、分子、分母和单位；说明结果变化的原因；最后给出适用范围、限制和下一步行动。不能只说“结果不同”，也不能把相关关系写成因果关系。

## 提高与拓展

完成标准路线后任选一项：

- **方法比较**：比较两个目标相同但假设不同的方法，说明为什么选择其中一个；
- **敏感性分析**：改变一个有实际依据的阈值、分母、时间范围或处理规则，画表说明结果如何变化；
- **复现检查**：从原始数据重新生成主要结果，增加重复键、范围、单位或分母检查；
- **决策说明**：面向另一类使用者写一页简报，说明哪些结论可以发布、哪些需要限制。

提高不是增加代码数量。好的提高任务会让读者更清楚结果在什么条件下可靠。

## 卡住时按顺序排查

1. 先确认在能看到 `scripts`、`data` 和本课目录的仓库根目录；
2. 确认命令中的课次编号、文件名和输出目录没有写错；
3. 保留完整命令和最后一段报错，不要删除旧结果来“清理”问题；
4. 数字对不上时，依次核对观测单位、筛选条件、缺失值、分母、单位和输出目录；
5. 报告无从下手时，先填写“问题—数据—方法—结果—限制—建议”六个小标题。

如果程序暂时不能运行，可以先完成手算和报告草稿，但必须标明“尚未运行”，修复后再补跑并更新数字。
