# 第5课 · 有限复核名额下的告警策略

## 项目背景

维护团队每天要从90台设备中选出少量复核对象：工作日最多20台，周末15台。故障损失和复核成本因设备类别不同。高分优先、超过统一阈值、兼顾高损失设备等规则可能产生不同后果。你需要提供下一周期可试运行的规则。

## 可用数据

见[告警数据说明](../data/alerts/README.md)：`development.csv` 42天，`evaluation.csv` 后14天，`devices.csv` 含成本与损失，`daily_capacity.csv` 含日容量。标签均是历史完整追踪结果。数据全部合成，分数不是故障概率。

本课数据均为教学合成数据，不代表真实机构。先阅读[知识准备](LEARN.md)，再选择分析方法。你可以全程使用AI完成代码、分析和写作；报告需解释主要结论的统计依据、适用条件和局限性。

## 分析任务

利用前42天数据制定满足每日名额限制的复核策略，并与一个有实际意义的备选方案比较。确定规则后保持不变，用后14天数据按日期模拟执行，评估错误率、复核成本和故障损失。提交每日复核名单的生成规则，说明适用条件，以及何时需要调整或停止使用。可以不使用全部名额，但不能超过当日上限。

### 必须遵守的约束

- 当日名单只能用行动前可知的信息，不能用该日之后才知道的故障结果选择复核设备。
- 情境规定复核可避免85%的故障损失；复核本身有成本。解释这是方案计算假设，不是从观察数据识别的干预效果。
- 不只报告总体准确率。报告容量使用、漏掉的故障及损失、无故障复核量，并给出分母明确的假阳性率/假阴性率。
- 规则可使用统一/分类阈值、排序、历史校准或其他方法；复杂模型不自动更好。
- 后一期参与调参后应注明为探索修订，不能继续称独立评估。

### 由你决定

你决定行动目标、得分到优先级的转换、并列处理和是否保留名额。至少考察一个会影响试运行建议的条件变化，例如容量、损失比例、复核效果或时期变化。

## 成果要求

- 写出别人可以按日执行的规则，任何日期均不超容量。
- 提供备选方案在相同记录和成本约定下的比较，而非只展示选中方案。
- 将方案制定期结果与后期结果分开，关键后果可追溯到日、设备类别或记录。
- 给出试运行、限范围试运行或暂不采用的建议，以及数值明确或可观察的监测条件。

在本目录的 `report.md` 中撰写分析报告，篇幅与结构可按问题需要调整。关键表、图或分析数据保存到 `artifacts/`，并在报告中引用。可以修改或替换 `analysis.py`；提供的示例代码只生成数据概览，不是本课的完整分析。

## 建议时间安排

0—13分钟读情境、错误率与损失例子；13—24分钟提出可比较规则；24—53分钟制定规则并用历史数据评估；53—68分钟比较不同条件下的结果，说明试运行的适用范围；68—75分钟核对提交；75—90分钟知识自查。可直接使用AI实现算法，优先比较真正影响行动的方案。

## 运行与提交

从仓库根目录运行：

```bash
python scripts/course.py start 05
python scripts/course.py run 05
```

完成报告和分析后，在 `submission.json` 填入支持报告结论的结果文件路径，将 `status` 改为 `complete`；如果更换运行入口，同步修改 `run`。运行 `python scripts/course.py check 05`，核对修改后提交并创建最终标签 `v2-l05-final`。完整步骤见[操作与提交步骤](../docs/WORKFLOW.md)。自动检查通过只说明文件、路径和运行命令符合提交要求，不代表统计结论正确。

最后约15分钟进入[知识自查](https://hblu.top/stat-check/)，确认页面显示当日第5课，按当前场次作答。建议先自行判断，不会时请AI解释概念再作答；使用方式见[自查说明](../docs/KNOWLEDGE_CHECK.md)。
